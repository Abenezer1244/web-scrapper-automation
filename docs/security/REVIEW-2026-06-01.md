## Deploy-blockers (Codex-confirmed)

### CRITICAL-1 — User-controlled webhook = SSRF + signed-URL exfiltration  ✅ FIXED (2026-06-01, Codex-verified PASS)
> Fix shipped: `validate_outbound_webhook()` (HTTPS-only + DNS resolution against an expanded blocked-IP set) called in the worker immediately before POST; blocked → `status:"blocked"`, no retry; `requests.Session(trust_env=False)` + `allow_redirects=False`; 3xx = non-retryable. Save-time structural HTTPS check in `DeliverConfig.webhook_url_format`. Tests: `tests/test_webhook_ssrf.py` (22).

`src/workers/webhook_delivery.py:169` POSTs to `DeliverConfig.webhook_url` (`src/api/schemas.py:121-130`), validated only by a format check (starts with `http(s)://`, ≤2000 chars) — **never `validate_scraping_target()`**. Dispatch at `src/workers/tasks.py:652-677`, and the payload embeds a 48h signed R2 download URL.
**Impact:** Any Business-plan user sets `webhook_url=http://169.254.169.254/...` or `http://localhost:6379/` and the worker fetches it from inside Railway's network — cloud IAM/metadata exfiltration, internal-service probing, plus the signed export URL is handed to an attacker endpoint. Codex: **REAL, Critical, fix first.**
**Fix:** Validate `webhook_url` through a dedicated outbound-webhook SSRF guard at config-save **and** in the worker before POST; HTTPS-only; resolve DNS + reject private/link-local/metadata IPs; disable/re-validate redirects. (Depends on HIGH-2 for the DNS piece.)

### HIGH-1 (keystone) — DNS rebinding defeats the SSRF firewall  🟡 PARTIAL (webhook path closed; scraper-side scheduled with HIGH-3/4/5)
> The DNS-resolution machinery now exists (`_assert_resolved_ips_safe`, `_ip_is_blocked`, expanded `_BLOCKED_NETWORKS`, `validate_scraping_target(resolve=...)`) and the **webhook path resolves** (`resolve=True`). Scraper navigation still defaults `resolve=False` — closing it means routing `navigate()`/`probe()` AND the 8 `page.goto` bypasses (HIGH-5) through `resolve=True` together and testing against live scrapes, so it's bundled into the HIGH-3/4/5 SSRF cluster (next phase). Codex flagged this as the one open item from the Phase-1 review; risk is constrained (scraper hosts are allowlisted `.gov`, not attacker-controlled).

`src/api/middleware/security.py:73-131` blocks only **literal** private/metadata IPs (`ipaddress.ip_address(hostname)`); for a hostname it does **no DNS resolution** (no `getaddrinfo`/`socket` anywhere in `src/`). `requests`/Playwright resolve at connect time → TOCTOU.
**Impact:** A hostname resolving to `169.254.169.254`/RFC1918 passes validation, then the client connects to the private IP. Codex downgraded from Critical→**High** (scraper path is allowlist-constrained), but this is the keystone: CRITICAL-1's fix is bypassable until this lands.
**Fix:** Resolve the host inside `validate_scraping_target()`, reject if any A/AAAA is in a blocked range; re-check after redirects; ideally connect-time IP pinning or network-level egress block.

### HIGH-2 — Production DB role bypasses RLS (the "belt" doesn't exist)
Deployed `postgres` role has `BYPASSRLS=true` (`tasks/progress.md:53,233`; `src/db/session.py:186-195` `check_rls_role_status`). RLS policies in migrations 001/018 are inert in prod; the **only** tenant boundary is the app-layer `WHERE user_id` filter. `tests/test_rls_isolation.py` proves the policies are correct under a `NOBYPASSRLS` role. Both reviewer and Codex: **REAL, High.**
**Fix:** Migrate the app to a `NOBYPASSRLS NOSUPERUSER` role + `FORCE ROW LEVEL SECURITY` on tenant tables. **Risky:** first audit/refactor `system_sync_session()` worker paths (tracerfy ingest, dispatcher, scheduler, daily scrape) so they don't break under the non-bypass role.

## Remaining High findings

### HIGH-3 — EagleWeb detail-page fetch bypasses firewall + forwards session cookies
`src/scrapers/templates/eagleweb.py:750` `requests.get(detail_href, cookies=...)` where `detail_href` is scraped from page DOM (`:580,594`) — no `validate_scraping_target()`. Malicious/MITM'd portal emits an internal `href`; worker fetches it with session cookies attached. **Fix:** validate `href` + restrict to the connector's allowlisted host before fetch.

### HIGH-4 — `county_connectors.gis_endpoint` fetched but never validated
`src/scrapers/enrichment/county_gis.py:161,201,236,431,513` `requests.get(gis_endpoint)`; the connector-create route (`src/api/routes/scrapers.py:334-354`) validates `base_url` but **not** `gis_endpoint`. Stored SSRF. **Fix:** validate `gis_endpoint` in `create_connector` exactly like `base_url`.

### HIGH-5 — 8 template `page.goto()` calls skip `navigate()` (no SSRF re-validation)
`eagleweb.py:156`, `acclaimweb.py:136,311`, `ava_fidlar.py:329`, `landmarkweb.py:170`, `whatcom_wa.py:137`, `king_wa_probate.py:444`, `enrichment/king_county_assessor.py:109`. The redirect-revalidation only lives in `self.navigate()`. **Fix:** route all navigation through `navigate()`; where raw `goto` is required, validate before + re-validate `page.url` after.

### HIGH-6 — `sanitize_for_csv` TAB/CR/LF prefix check is dead code
`src/api/middleware/security.py:268-282`: `clean_text()` strips/replaces `\r\n` and `.strip()`s **before** the `startswith(("=","+","-","@","\t","\r"))` check, so the tab/CR/LF entries can never match (and `\n` isn't even listed). `= + - @` still caught (so High not Critical), but the function silently no-ops part of its advertised contract. **Fix:** run the prefix check on the **raw** value before `clean_text`, add `\n`.

### HIGH-7 — E2E credential files evade `.gitignore`; live password on disk
`scripts/.e2e_king_creds.json` (+ `.e2e_pierce_live.json`, `.e2e_king_job.json`) don't match the `.gitignore:117-120` patterns (which list `.e2e_creds.json` etc.) → untracked, one `git add scripts/` from being committed. Contains a **live** prod password `KingDemo!2026` (JWTs in them are expired). Not yet committed. **Fix:** broaden ignore to `scripts/.e2e_*.json`; rotate `KingDemo!2026`.

### HIGH-8 — API-key auth bypasses logout-all / revocation entirely
`src/api/auth.py:122-145`: the API-key path returns the user after the hash lookup, never calling `is_blacklisted`/`is_revoked_by_user_logout_all` (the JWT path does). `/auth/logout-all` has **no effect** on a leaked API key. **Fix:** make `revoke_all_for_user` also null/rotate `api_key_hash`; document key rotation as the revoke path.

### HIGH-9 — Stripe `user_message` leaked to client
`src/api/routes/billing.py:427-431` returns `detail=f"...: {exc.user_message}"` verbatim (the `/checkout` path does this correctly). Violates the reference-id error rule. **Fix:** log + return a generic message with a reference id.
