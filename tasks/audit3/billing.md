## Duplicate subscriptions

How the code prevents a second subscription:
1. `/billing/checkout` and `/billing/change-plan` take the same transaction-scoped `pg_advisory_xact_lock(4243, hashtext(user_id))` (`billing.py:1053-1057`, `:1459-1462`), then re-read the user under the lock (`:1063-1064`, `:1464-1465`). The skip-trace meter reporter tries the same lock and yields (`src/workers/tracerfy_ingest.py:118-129`).
2. The guard asks Stripe, never `users.plan`: `_live_subscription` lists `status="all"` and treats everything except `canceled` and `incomplete_expired` as live, so an unknown future status blocks (`billing.py:832`, `:864-886`). A listing failure raises and becomes 503 (`:1180-1194`).
3. Open subscription-mode Sessions for the customer are expired, then Stripe is asked again (`:1098-1109`); after the new Session is created Stripe is asked a third time and the new Session is expired if a subscription appeared or the answer is unknown (`:1141-1168`).
4. The customer is adopted by exact `metadata.user_id` across all pages of `Customer.list(email=...)` (`:844-861`), so the guard enumerates the right customer.
5. `change-plan` modifies the existing subscription in one `Subscription.modify` call and never creates one (`:1409-1654`); without a customer or a live subscription it returns 409 (`:1467-1479`). No other code path creates a subscription or Session (grep of `Subscription.create`, `Session.create`, `PaymentLink`, `SubscriptionSchedule` in `src/`).

Measured:
- Second checkout with an existing subscription in each of `active`, `past_due`, `unpaid`, `incomplete`, `paused`, `trialing` and an invented `some_new_status`: 409 every time (`subscription_incomplete` for `incomplete`, `subscription_exists` otherwise).
- Stripe listing unavailable: 503, no Session.
- Three concurrent checkouts for one user with three different prices: three 200s, one Session left open (the other two expired by the later requests).
- Checkout racing `change-plan` on an active subscriber: checkout 409, change-plan 200.

How a duplicate is detected if one slips through (a Session already being paid in the gap): `checkout.session.completed` compares the new subscription with `users.stripe_subscription_id` and pages ops when the recorded one is still live (`:2027-2052`). That detection is bypassed by the usual event order: `customer.subscription.created` or `.updated` for the new subscription normally arrives first and rebinds `stripe_subscription_id` to it (`:2284-2312`, `billing_entitlement.py:265`), so the later comparison sees the same id and stays quiet. Reproduced: alert fired only when `checkout.session.completed` came first (BI-3). `subscription.deleted` for either one keeps the account on the survivor (`billing.py:2358-2392`), so no customer is wrongly downgraded; the gap is that a double charge goes unnoticed.

## Tracerfy

- **Credentials server-only.** `TRACERFY_API_TOKEN` is read only by `submit_batch` / `fetch_queues` in the worker (`src/scrapers/enrichment/skip_trace.py:560`, `:689`) and the dispatcher's presence check (`src/workers/skip_trace_dispatcher.py:43`); sent as a header with `trust_env=False`, `allow_redirects=False`, HTTPS enforced and an SSRF check (`skip_trace.py:560-580`, `:625-634`). No API route calls Tracerfy or returns either Tracerfy setting (grep over `src/api` and `main.py`). `TRACERFY_WEBHOOK_SECRET` must be at least 24 characters (`src/config/settings.py:367-376`).
- **Quota enforcement.** Skip trace is gated on plan only (Starter excluded) at save time and run time (`src/workers/tasks_helpers/enrich.py:2280-2292`). Trial accounts are `plan="pro"` (`src/api/routes/auth_helpers/registration.py:188`) and pass: leaf 1.3 **AZ-2 (P1)**. Bundled quota and overage are counted per completed batch under the user row lock (`src/api/billing/skip_trace_usage.py:41-191`) and overage is released to Stripe only by `assert_billable` (`:290-427`). The only spend ceiling is global, soft and row-based (BI-2).
- **Input validation.** The webhook requires a JSON object with an integer `id` (`src/api/routes/webhooks.py:77-111`; `true` also passes `isinstance(int)`, harmless). `rows_uploaded` and `credits_deducted` are passed to the worker unvalidated (`:144-149`) and overwrite the dispatcher's values (BI-1). What we send to Tracerfy is lead data from public records, not user input (`skip_trace.py:587-617`).
- **Response sanitization.** Provider phones and emails are stored as returned (`skip_trace.py:750-822`); CSV export normalises phones to digits and passes email, type and names through `sanitize_for_csv` (`src/utils/lead_export.py:584-592`). The provider `raw` row goes only to the cache table and is not served by any API route (grep `raw_response` in `src/api`).
- **Errors.** `TracerfyError` text (which can carry up to 500 characters of provider body, `skip_trace.py:650-651`) stays in worker logs, the dispatcher's task result and ops alerts (`skip_trace_dispatcher.py:361-363`, `:431`); no user-facing route or job log receives it (grep of `_publish_log` / `error_message` in the dispatcher). The token is sent in a header, not the URL, so a `requests` exception string does not include it.
- **Webhook `/webhooks/tracerfy`.** Header route: rate limit, then constant-time compare of `X-Tracerfy-Webhook-Secret` (`webhooks.py:51-71`, `:154-166`). Tested: no header 401, wrong header 401, right header 200, non-object body 400. Legacy `/webhooks/tracerfy/{secret}` is enabled by default and accepted the path secret (200); a wrong header beats a right path secret (401) (`:169-217`, `settings.py:345`) (BI-7).
- **rows_uploaded trust.** The body value overwrites `skip_trace_queues.rows_uploaded` (`src/workers/tracerfy_ingest.py:831-841`) and is then what decides whether `unmatched` rows are billed (`skip_trace_usage.py:611-624`). The download host pin accepts `http` and any DigitalOcean region whose first label is `tracerfy` (`tracerfy_ingest.py:440-454`; harness: `http://tracerfy.nyc3...`, `https://tracerfy.fra1...`, `https://tracerfy.sgp1.cdn...` all accepted, `tracerfy.com.evil.com` refused) (BI-1).
- **Replay and double charge.** The same batch ingested twice: a pre-download status peek and then `SELECT ... FOR UPDATE` on the queue row no-op once `completed`/`billed`/`errored`, and the counter advance, row flips and status flip commit in one transaction (`tracerfy_ingest.py:519-536`, `:571-593`, `:853-877`). Meter outbox rows are unique per (queue, user) with a stable Stripe identifier (`skip_trace_usage.py:537-700`, `tracerfy_ingest.py:57-58`), and the reporter claims only `pending` rows under a row lock (`:130-159`). Retries after a timeout: the claim (`submitting`) is committed before the POST and a read timeout keeps it for the reconciler, never auto-resubmitted (`skip_trace_dispatcher.py:338-371`, `:1599-1640`). The residual: a dropped connection after the body was sent, and 5xx responses, are classified as "not delivered" and resubmitted (BI-6, operator cost, not customer).
